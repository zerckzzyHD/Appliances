# Conditional analysis-tool evaluation: proposal only

This procedure implements the selection gates in [the plan](../plan.md). Tool
findings and the LeanREA benchmark ceiling live in [the assessment](../research/rea.md).
No tool installation, fixture, runner, config change or target analysis exists
because this protocol was written. G1 remote-input testing is independent.

## Question and eligibility before any tooling work

Name one product question first: for example G2's normalizer-to-launch relation
or G3's Home-route consumer. Specify the exact eligible artifact, required
relationship evidence, known controls, useful decision and output/privacy scope.
Use direct inspection if it answers the question; stop there. Missing artifact
access is not solved by installing REA. Separate unavailable input from an
analysis limitation on input we actually have. A synthetic fixture may assess
tooling but cannot itself advance product G2/G3 evidence. Ordinary complete source is read with
normal repository tools, not routed through REA as a matter of ceremony.

If a REA trial remains useful, first review and obtain approval for pinned
rea-agents6.8.0 acquisition, dependency/install behavior, network origins and
exact write footprint. Proposed ignored home: .local/rea under this repository,
with scoped package cache/runtime/scratch and no root package dependency change.
No setup, MCP registration, global skill, Linux distribution, driver or native
analysis engine is included. Check scope against the actual package before
installation; record any unavoidable cache/output outside the proposed home.

## Capability gate

After installation is authorized, inspect shipped command schemas/capabilities
and the selected lane's Windows requirements. A green general doctor would not
establish every engine or firmware capability. Missing support stops that lane;
propose the minimum remedy separately rather than installing a whole toolchain.
Preserve package identity/integrity and dependency records. Never execute an
acquired target just because its static processing was authorized.

## Smallest trial if needed

1. Define a tiny synthetic application with known normalization -> launch ->
   request and Home-route-consumer relationships plus disconnected decoy strings.
   It must contain no TV source, credentials or live endpoints. A directory input
   follows the static application's actual admission; do not assume a single JS
   file selects that workflow.
2. Answer the same fixed questions by direct inspection, recording input hashes,
   source locations, positive relationships, decoys, gaps and bounded output.
   Existing approved tools are the baseline; no automatic npx downloads.
3. Run pinned REA CLI against the identical input/questions after choosing finite
   time, memory and output controls supported by its actual schemas. Record all
   limits and partial output. Do not silently raise budgets or weaken integrity
   handling to get a result. Do not treat source/strings as runtime observations.
4. Compare actual relationships and source locations against ground truth. Count
   missing edges, false-positive decoy links, unknowns and coverage, not just
   keywords. Record wall time and output size; separate acquisition/cold startup
   from repeat work. Model usage/cost is unknown unless directly measurable.
   A small trial is not a general speed/cost benchmark.
5. Keep REA only if its additional source-bound relationship/coverage evidence
   justifies the overhead for the named question. If direct tools suffice or
   results are misleading/unsupported, retain the direct path and stop setup.

No standalone benchmark framework or routine HAR/SQLite fixture suite is planned.
Those lanes resume only for a plausible artifact/question. No blanket LeanREA
skill installation is required to use selective inspection practices.

## Real-artifact and integration gates

After a useful trial, establish the selected real artifact's provenance, exact
version, acquisition authority, permitted processing/retention and bounded
outputs. Acquisition does not authorize replay, contacting embedded URLs or
retaining raw private source. Retired SDK/test-UI/Home capture grants stay retired.
Synthetic success cannot recover missing source or prove TV privileges.

Only then consider MCP if persistent retained queries or agent access offer a
measured benefit. Prepare a selected-client config diff, private backup/readback,
permissions/tool exposure, process lifecycle and exact rollback. CLI success
is not permission for configuration changes. Prefer stdio/local integration;
no new HTTP/LAN server, blanket active-tool access or multi-client setup.
Never represent descriptive read-only annotations as enforced permissions.

## Stop, evidence and handover

Stop on scope/provider expansion, mutable input mismatch, unexpected networking,
ambiguous output, unresolved cleanup or inability to distinguish a decoy. Keep
original inputs and prior evidence; cleanup only owned scratch under an exact
reviewed path, without erasing a previous run. No shared-temp recursive deletion.

Record tool/version, artifact hashes, supported host/provider facts, actual
commands and results, controls, residual unknowns and next product decision.
Commit only approved sanitized evidence; retain no target raw source or secrets
by implication. Update plan/status and affected protocol rather than inventing
another current queue. The executor handles keyboard work after authorization;
owner presence is required only for the separately scoped physical TV test.
